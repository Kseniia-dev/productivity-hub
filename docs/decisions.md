# Decisions

## 2026-08-28

### Решение: использовать React + TypeScript + Vite для frontend

**Что решила**

Frontend MVP будет разрабатываться на React с TypeScript и Vite.

**Почему**

React подходит для интерфейса с большим количеством состояний: задачи, календарь, фокус-таймер, авторизация, личный кабинет и админ-панель.

TypeScript помогает раньше находить ошибки в данных и лучше понимать структуру проекта.

Vite даёт быстрый запуск проекта и удобную разработку frontend-приложения.

**Альтернативы**

Можно было использовать Vue, Angular или обычный JavaScript без TypeScript.

**Последствия**

Нужно изучить компоненты React, состояние, props, события, React Router, работу с API и основы TypeScript.


### Решение: использовать Python + FastAPI для backend

**Что решила**

Backend MVP будет разрабатываться на Python с FastAPI.

**Почему**

FastAPI хорошо подходит для REST API, автоматически создаёт документацию API и удобно работает с Pydantic-схемами для проверки данных.

Python выбран как основной язык backend, потому что он понятный для изучения и подходит для дальнейшего расширения проекта.

**Альтернативы**

Можно было использовать Django, Flask, Express.js или NestJS.

**Последствия**

Нужно изучить основы FastAPI, routes, schemas, dependencies, status codes, обработку ошибок и подключение базы данных.


### Решение: использовать PostgreSQL как основную базу данных

**Что решила**

Данные зарегистрированных пользователей будут храниться в PostgreSQL.

**Почему**

PostgreSQL подходит для проекта с пользователями, задачами, ролями, фокус-сессиями, статистикой и будущими связями между сущностями.

Эта база лучше подходит для роста проекта, чем хранение данных в файлах или только в браузере.

**Альтернативы**

Можно было использовать SQLite, MySQL или MongoDB.

**Последствия**

Нужно изучить таблицы, связи, primary key, foreign key, SQL-запросы и миграции.


### Решение: не сохранять guest-данные на backend

**Что решила**

Гость может создавать задачи и запускать фокус-сессии, но эти данные не сохраняются на backend.

**Почему**

Guest-режим нужен, чтобы пользователь мог быстро попробовать приложение без регистрации.

Если сохранять guest-данные на backend, пришлось бы создавать временных пользователей, связывать их с задачами и переносить эти данные после регистрации. Для MVP это усложняет проект.

**Альтернативы**

Можно было сохранять guest-данные в backend через временный guest-id или полностью запретить гостям создавать задачи.

**Последствия**

Guest-данные будут храниться только на frontend. Нужно будет показать предупреждение, что для сохранения прогресса нужно зарегистрироваться.


### Решение: сначала сделать web-приложение, desktop — после MVP

**Что решила**

Сначала будет разработано web-приложение. Desktop-версия будет рассматриваться после готовности MVP.

**Почему**

Web-версия проще для первой разработки, тестирования и проверки идеи. Desktop-приложение добавит отдельный слой сложности: упаковку, обновления, работу с системой и дополнительные зависимости.

**Альтернативы**

Можно было сразу делать desktop-приложение на Tauri или Electron.

**Последствия**

Frontend и backend нужно строить так, чтобы позже их можно было переиспользовать в desktop-версии.




## 2026-09-07

### Решение: использовать email и password для авторизации

**Что решила**

Пользователь регистрируется и входит через email и password.

**Почему**

Это понятный и привычный способ авторизации. Он подходит для MVP и не требует внешних OAuth-провайдеров.

**Альтернативы**

Можно было использовать username + password, вход через Google, GitHub или magic link.

**Последствия**

Нужно хранить email, хэш пароля, делать проверку пароля при входе и защищать приватные страницы.


### Решение: перенести восстановление пароля после MVP

**Что решила**

Восстановление пароля не входит в MVP.

**Почему**

Восстановление пароля требует email-отправки, токенов восстановления, срока жизни ссылок и дополнительной защиты. Это важная функция, но она не нужна для проверки главной идеи MVP.

**Альтернативы**

Можно было включить восстановление пароля в MVP.

**Последствия**

В MVP пользователь сможет зарегистрироваться, войти и сменить пароль внутри личного кабинета, если он уже авторизован.


### Решение: не отмечать задачу выполненной автоматически после фокуса

**Что решила**

После завершения фокус-сессии приложение предлагает пользователю отметить связанную задачу как done, но не меняет статус автоматически.

**Почему**

Пользователь мог провести время в фокусе, но не завершить задачу. Автоматическое завершение задачи может давать неправильную статистику.

**Альтернативы**

Можно было автоматически менять статус задачи на done после завершения фокуса.

**Последствия**

Frontend должен показать пользователю предложение отметить задачу выполненной после завершения фокус-сессии.


### Решение: хранить даты и время в едином формате

**Что решила**

Все даты и время в backend будут храниться в едином формате, чтобы задачи, фокус-сессии и статистика работали предсказуемо.

**Почему**

Проект зависит от календаря, времени начала задач, длительности и истории фокус-сессий. Если хранить время хаотично, позже будет сложно считать статистику и восстанавливать активный таймер.

**Альтернативы**

Можно было хранить даты и время как обычный текст или разными форматами в разных частях приложения.

**Последствия**

Нужно изучить типы даты и времени, timezone, формат ISO, а также разницу между датой, временем и datetime.
